# 产品案例：用实验数据做知识库方案决策

[English](case-study-product.en.md) · [返回首页](../README.md) · [完整报告](../experiments/report/REPORT.zh-CN.md)

这是一份决策复盘：一个实时语音问答产品要不要上 RAG、上什么样的 RAG。重点不在技术细节，而在**怎么把模糊的问题变成可测的假设，再把数据变成产品决策**。

## 1. 用户和问题

**场景**：用户在对话中实时收到 AI 生成的、可以直接说出口的回答。回答要参考用户自己导入的资料，比如简历、岗位描述、几万到几十万字的笔记。

**用户最在意的三件事**：

| 用户的感受 | 对应的产品指标 | 门槛 |
| --- | --- | --- |
| “说完半天还没出字，等于没用” | 首个回答字延迟（TTFT） | 对方说完后 2 秒内，扣掉语音识别和断句，留给模型的不到 1 秒多 |
| “答非所问、张冠李戴” | 完全正确率、答错率 | 越高越好，答错比“说没有”更伤 |
| “我的资料会不会被传出去”“用一次要多少钱” | 是否上传资料、每题费用 | 默认不上传；每题控制在分钱级 |

**团队面临的选择**：行业里的默认方案是“RAG + 向量库 + Agent 框架”。但这套方案会带来额外延迟、依赖体积和隐私问题。在没有数据之前，“该不该上”只能靠感觉。

## 2. 把问题拆成可以测的假设

| 编号 | 假设 | 如果成立，产品怎么做 | 如果不成立 |
| --- | --- | --- | --- |
| H1 | 资料不大时，整包发送比检索更准，且成本可接受 | 先整包，提高整包上限 | 尽早引入检索 |
| H2 | 检索方法的差距比“整包还是检索”更大 | 检索时优先投入在方法上 | 随便选一种即可 |
| H3 | 语音识别错字会明显拖累关键词检索 | 实时语音场景优先向量检索 | BM25 足够 |
| H4 | 本地小向量模型足够好 | 默认本地，不上传资料 | 默认云端，需要隐私告知 |
| H5 | 主流框架能带来质量提升 | 引入框架 | 手写，保持轻量 |
| H6 | “会翻目录”的 Agent 式检索（PageIndex）明显更好 | 作为新方案引入 | 只在特定场景使用 |
| H7 | 缓存能同时降低成本和延迟 | 围绕缓存设计提示词 | 只当省钱手段 |

## 3. 实验设计：先保证结论可信

- **用公开数据**：选公开的中文技术笔记，不用任何真实用户资料，结果可以公开、可以复现。
- **让失败暴露出来**：要求模型“只根据资料回答，找不到就说没有”。检索漏掉关键段，就直接变成答错，不会被模型的常识掩盖。
- **控制变量**：每个实验只改一个因素，比如只换检索方法、只换模型、只改资料大小。
- **说清不确定性**：每组几十道题，结论都带 95% 区间；比较两个方法时按题配对。区间跨 0 就如实写“差异不显著”。
- **控制成本**：先跑小规模预检，按实测单价推算全量成本，超出预算就停下来重新申请。最终第二轮 3043 次请求，花费 ¥9.39，总预算 ¥20。

## 4. 结果和决策

| 假设 | 关键数据 | 产品决策 |
| --- | --- | --- |
| H1 成立 | 整包在 8.5 万字以内答对率稳定在 75%；同领域资料超过 10 万字后才下降；每题不到 1 分钱 | **整包上限从 3 万字提高到 6 万字**，留出余量 |
| H2 成立 | 同样 20 万字：BM25 完全正确 46%，云端向量 69%；每次给 5 段比 3 段高 6–12 个百分点 | **每次检索从 3 段改为 5 段**；检索投入放在方法上 |
| H3 成立 | 语音风格的问题下，BM25 找对段落从 65% 掉到 52%，向量只从 94% 掉到 85% | 实时语音场景**优先向量检索** |
| H4 成立 | 本地 Qwen3-Embedding 与云端 DashScope 基本持平（95.8% vs 97.9%） | **默认用本地向量（bge-small，不上传资料）**；云端向量需要用户明确点击后才上传；有显卡的用户增加 Qwen3-Embedding 选项（排入后续） |
| H5 不成立 | 框架配好后与手写同一水平；中文默认配置几乎失效；多出 346 MB 依赖；Agent 循环费用约 15 倍、无显著提升 | **不引入框架**，保持几百行手写实现；单跳问答不用 Agent 循环 |
| H6 部分成立 | PageIndex 比 BM25、向量明显更准，但和整包差异不显著；每题多约 5 秒、贵 6–7 倍 | **实时场景不引入**；作为会后复盘、离线问答的候选方案 |
| H7 部分成立 | 前缀缓存让整包输入费用降约 96%，首字没有稳定变快 | 提示词按“稳定前缀 → 资料 → 问题”分层，并在开始前发预热请求；**把缓存当成本手段，不当延迟手段宣传** |

## 5. 取舍和风险

- **准确 vs 速度**：更准的云端模型（qwen3.8-flash / 3.7-plus）整包首字接近 3 秒。决策是实时场景用首字快的模型，非实时任务（复盘、写资料）再用更准的模型，而不是二选一。
- **隐私 vs 效果**：云端向量略好，但要上传资料、要花钱。决策是默认本地，云端由用户明确选择。产品文案里如实说明差别，不夸大。
- **供应商风险**：实验期间，第一轮用的 deepseek-chat 被服务商下线了。这说明模型选择必须可替换：接口统一走 OpenAI 兼容格式，模型名和价格放进配置，并且新旧模型的结果不能混在一起比。
- **评测的局限**：题目由模型生成，评分模型和回答模型来自同一家，样本量不大，语音噪声是模拟的。所以结论只用来指导方向，并标明适用条件，不当作普适结论。

## 6. 如果重做一次

- 先做**真实用户资料的小样本验证**（在用户授权下），确认公开语料的结论能迁移。
- 加入**人工抽检评分**，校准“模型当评委”的偏差。
- 用**真实语音识别结果**代替模拟噪声。
- 从一开始就为 PageIndex 这类慢方法设计**异步体验**（先给简短回答，再补充详细版），而不是只拿同步首字延迟来比较。

## 7. 我在这个项目里的角色

- 定义问题和指标：把“要不要上 RAG”拆成 7 个可测假设，明确首字、准确率、费用、隐私四个维度。
- 设计和执行实验：13 组实验，控制变量，给出区间和配对比较。
- 管理成本和风险：设定总预算和分阶段上限，预检后按实测推算，超支前停下来调整。
- 把数据变成决策：两项参数改动直接落地（整包上限 3 万 → 6 万字、每次检索 3 → 5 段），并为“本地向量优先、云端需用户同意”“不引入框架”这两个设计提供了数据依据；每项都写清了依据和适用条件。
