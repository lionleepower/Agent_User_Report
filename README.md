# 小资料先别急着上 RAG

**个人知识库的检索、模型与框架实测**

[English](README.en.md) · [实验详解](experiments/report/WALKTHROUGH.zh-CN.md) · [完整报告](experiments/report/REPORT.zh-CN.md) · [小白手册](experiments/report/HANDBOOK.zh-CN.md) · [产品案例](docs/case-study-product.zh-CN.md) · [工程亮点](docs/engineering-highlights.zh-CN.md)

## 概览

**要解决的问题**：我的一个个人项目要做实时语音问答。对方说完一句话，程序要从我自己的笔记里找到相关内容，让 AI 生成一段能直接说出口的回答，而且最好 2 秒内开始出字。那么，AI 该怎么“查资料”？

**做了什么**：用一份公开的中文技术笔记出了上百道题，比较了 4 种让 AI 查资料的方式、9 个回答模型、3 个向量模型和 3 个主流框架，每道题都让另一个 AI 按标准答案打分。

**三句话结论**：

1. **资料不多（6 万字以内）时，直接把全部资料交给 AI，比任何“查资料”的办法都准**，而且借助缓存，每题不到一分钱。
2. **资料多了要查，按“意思”查（向量检索）比按“关键词”查准得多**，尤其是问题来自语音识别、带错别字的时候。
3. **更复杂的方案（让 AI 自己翻目录、用 Agent 框架）确实更准一些，但每题要多等好几秒**，不适合实时场景。

## 核心结论

1. **资料不多时，整包发给模型就是最好的“检索”。** 6 万字以内放心整包，8.5 万字以内答对率不变（75%），前缀缓存命中 97–98%，每题不到一分钱。
2. **检索时别只靠关键词。** BM25 完全正确 46–67%，向量检索 74–96%；语音识别的错字还会让 BM25 再掉十几个点。
3. **本地向量模型已经够用。** Qwen3-Embedding-0.6B 在笔记本显卡上和云端 DashScope 打成平手（找对段落 95.8% vs 97.9%）。
4. **PageIndex 像认真翻目录的好学生，也像好学生一样慢。** 比 BM25 高 21–33 个百分点、比向量高 17–20 个百分点，但和整包差异不显著，每题多花约 5 秒、贵 6–7 倍。
5. **实时场景看首字，非实时场景看准确。** 推理模型会先“想”一分多钟，不适合实时。
6. **框架没有魔法。** 配好之后和几百行手写代码同一水平，但中文默认配置基本不可用，还要背上 346 MB 依赖。
7. **缓存省钱，不一定省时间。** 本地 q8_0 让 KV cache 启动分配量少 46.875%；云端前缀缓存让整包输入费用降约 96%，首字却没有稳定变快。

## 举个例子：同一道题，四种方法答得怎么样

问题：“有个二维数组，每行从左到右递增、每列从上到下也递增，怎么在里面高效找一个目标数？”（真实实验题，改编自 CS-Notes）

| 方法 | 得分（0–2） | 回答（节选） |
| --- | --- | --- |
| 整包 | 2 | 从右上角开始找：目标比当前值小就往左走，比当前值大就往下走……O(m+n) |
| BM25（关键词） | 0 | 资料中没有相关内容。 |
| 向量（按意思） | 0 | 资料里提到了 Leetcode 240 有序矩阵查找，但只给了题目和示例矩阵，没有具体解法。 |
| PageIndex（翻目录） | 2 | 从右上角开始找……最多走 m+n 步 |

问题换了说法，关键词对不上，BM25 没找到；向量检索找到了对的那一节，但模型看到的内容里只有题目、没有解法。**“找到了”不等于“答对了”。** 更多真实例子（语音错字、跨章节组合题）和每个实验的详细说明，见[实验详解](experiments/report/WALKTHROUGH.zh-CN.md)。

## 实验是怎么做的

![一道题的完整旅程](experiments/report/figures/eval-pipeline.svg)

- **题目**：从公开笔记的段落出题，每题记下 2–4 个答案要点和标准答案所在的段落。题型有四种：直接问、换说法、语音识别噪声版、跨章节组合。
- **严格回答规则**：模型只能根据给它的资料回答，找不到就说“资料中没有”。这样“资料没找对”会直接变成“答错”，不会被模型的常识掩盖。
- **评分**：另一个模型对照要点打 0 / 1 / 2 分，主指标是得 2 分的比例（完全正确率）。每道题答两遍先平均，失败算答错，再按题算 95% 区间，两种方法按题配对比较。
- **13 组实验**：

| 实验 | 想回答的问题 |
| --- | --- |
| 01 / 01b 资料规模 | 资料多大时，整包开始答不准？同主题资料呢？ |
| 02 框架 | LangChain、LlamaIndex 配好后能不能比手写好？ |
| 03 语音噪声 | 识别错字会让检索掉多少？ |
| 04 切段 / 06 段数 | 资料怎么切、每次给几段最好？ |
| 07 回答模型 | 9 个云端和本地模型，谁又快又准？ |
| 07b 向量模型 | 本地小模型能不能替代云端？ |
| 08 LangGraph | 让 Agent 自己决定怎么查，值不值？ |
| 09 并发 | 很多人同时问会不会变慢？ |
| 11 PageIndex | “翻目录”式检索到底好不好？ |
| 12 缓存 | 本地 KV cache 和云端前缀缓存能省多少？ |

- **成本控制**：自己写了一个跨进程的预算网关，所有付费请求先按上限预留、拿到用量再结算，SDK 内部的调用和重试也逃不出预算。第二轮共 3043 次请求，按用量计 ¥9.39。
- **结论落地与依据**：整包上限从 3 万字提高到 6 万字；每次检索从 3 段改为 5 段（完全正确率 +6–12 个百分点）；不引入框架；本地 bge 向量为默认、云端向量需要用户明确同意。

## 关于可复现性

- 代码是**快照**，用于阅读和审查。部分脚本依赖原项目的内部模块（检索实现、密钥读取工具），单独拷出来不能直接运行。
- 所有图表都由 `experiments/report/` 下的脚本，从各实验的 `results/*.json` 生成。数字可以逐个追溯到汇总文件。
- 完整题库、原始回答、评分原文和语料正文不在仓库里：它们会引用语料原文，而且语料有独立的许可。
